# End-to-end classification and training framework

Date: 2026-10-17. Scope: reusable product infrastructure, not a newly trained
customer classifier. The previous Laya-first benchmark continues separately.

## Product boundary

The deliverable is a configurable local classification pipeline and its learning
lifecycle. Development can use clearly marked AI-authored/AI-reviewed labels.
Independent expert customer labels are not a prerequisite for building exports,
trainers, evaluation, calibration, checkpoint loading, review or audit mechanisms.
They remain necessary for a later customer-accuracy claim. Automation is disabled.

Existing inference boundaries remain: optional Prowide/recovery, deterministic
facts/deadlines, model adapters, reconciliation, evidence, review and audit. The
new training boundary does not change the active benchmark models or prompts.

## Implemented in this increment

* A shared nine-predicate annotation contract with untouched text/hash, exact
  evidence, duplicate group/family, language, split and label provenance.
* Explicit AI_AUTHORED, AI_REVIEWED, HUMAN_REVIEWED and EXPERT_REVIEWED origins.
  AI identities are required; AI reviews cannot attest human expertise. Existing
  complete-schema review revisions remain append-only and store previous AI output.
* Train/validation-only export to both official Laya choice format and local-LLM
  assistant JSON format. Temporal comparison and numerical confidence are not
  training targets. Positive training labels require exact-source evidence.
* Source/count/checksum/target checks and exact, normalised, lexical-near-duplicate,
  source-group and generation-family separation. Protected test/calibration paths
  are rejected. Original corpus and historical checkpoints are unchanged.
* Official Laya SDK fine-tuning, separate validation, disabled internal random
  calibration, context-loss checks and checkpoint reload probes.
* Generic offline Transformers/PEFT LoRA: masked assistant-target loss, explicit
  context limits, seed, validation loss curve, safetensors save/reload parity.
  Qwen and GLM are selectable model configurations. Unsupported exact models fail
  explicitly; no remote code or automatic weight download is enabled.
* Immutable job plans and append-only events with dataset/base/source identities,
  package versions, hyperparameters and hardware. A resource lease and benchmark
  guard prevent training from competing with active timed inference studies.
* Experimental checkpoint registration and common reload/validation evaluation.
  Validation predictions are saved before scoring; field supports, critical
  affirmative recall and confusion matrices use the shared assertion evaluator.
  New checkpoints are not silently deployed and do not inherit an old calibrator.
* API status/job preparation and Model Lab visibility. The review form records
  AI/human provenance and exact evidence. Opening a page does not train a model.

## Real training proof and its limit

The PEFT engine executed a real CPU LoRA optimiser update against a random tiny
GPT-2 architecture created locally for the test: one layer, 16-dimensional hidden
state, 128 trainable adapter parameters. No model weights were downloaded. The
adapter was written to safetensors and reloaded; maximum probe logit difference
was 0.0. The complete test took 6.68 seconds; its measured optimiser/validation/
save/reload section took about 0.18 seconds. This is execution evidence only,
not semantic quality or Qwen/GLM checkpoint compatibility.

Test environment: PEFT0.21.2, Accelerate1.15.0, Transformers5.20.0,
Torch2.14.1, Laya0.4.8. Optional training packages were installed under an isolated
artifact directory, leaving the running inference environment unchanged.
Receipt: `artifacts/training-framework-real-smoke.json`.

The existing official Laya training history is retained. No new Laya/Qwen/GLM
production-candidate weights were trained in this increment. The new Laya trainer
contract was tested with an explicit double; this report does not claim a new
real Laya training run or its reload probe was executed.

## Initial LLM choice and exact-model qualification

Use Qwen as the first configured training/inference candidate based on the
completed internal authored benchmark, while retaining GLM as an interchangeable
candidate. That choice is provisional and is not a customer-quality claim.

Prepared plans:

* `laya-framework-v1`: prerequisites available; execution not started.
* `qwen-framework-v1`: blocked on a compatible local trainable checkpoint and
  optional training dependencies in its execution environment.
* `glm-framework-v1`: additionally requires an exact base revision to be pinned.

The installed Ollama Q4 GGUF is not a directly trainable PEFT checkpoint. This
initial backend implements ordinary LoRA, not a claimed working 27B quantised
trainer on the 64GB Mac. Full27B ordinary weights leave insufficient training
headroom under the conservative preflight budget. The next model-specific task
is to qualify a compatible quantised-training backend/checkpoint locally, or run
the pinned trainer on a suitably provisioned training host. Inference remains
local-capable. A preflight PASS checks prerequisites, not exact-model correctness.

## Verification and remaining boundaries

The initial complete software regression run passed 2,141 tests, with one opt-in
CPU training test skipped and155 model/browser cases deselected. The separate
real CPU training test passed. Subsequent focused and browser results are recorded
in the final verification receipt alongside this report; model-quality failures
are not counted as application-test passes.

One first-pass browser check failed because the new panel duplicated an existing
status sentence, making its locator ambiguous. The panel wording was changed;
the existing assertion was retained. No frozen semantic answer was changed.

Software tests and the tiny CPU smoke overlapped the ongoing validation study;
those intervals must not be presented as uncontended inference latency evidence.
No training job was automatically started or queued to start after the benchmark.

Still to qualify: real training/reload for the selected Qwen/GLM checkpoint;
quantised-training feasibility on this Mac; trained-model integration into a
selected serving/cascade policy; model-specific semantic evaluation, damage
analysis and fresh calibration. The registered Laya whole-notice decision adapter
currently marks model quotation evidence unavailable rather than inventing it;
promotion needs the existing passage/evidence layer to be evaluated with the new
checkpoint. General distributed scheduling, full optimiser-state resume and
automatic checkpoint promotion are not implemented by this increment.

These are engineering qualification tasks that can use AI-labelled development
data. They need not wait for a human-labelled customer corpus. Real-data quality
and customer automation remain a separate later gate.
